# 语音信号探针（bw-voice-signal-probe）

电脑语音链路的**只读诊断工具**。不打包、不部署、不参与任何交付物 ——
它存在的唯一目的是：出问题时**能看见发生了什么**。

2026-08-18 排查「语音总是打不开 / 打开又闪退 / 有时要重启 Codex」时写的。
那次绕的弯路很长，而绕弯的原因全是同一个：**看不见**。这个工具就是那次的沉淀。

## 怎么跑

```
C:\Users\bwica\bw-computer-voice-bridge\dotnet8\dotnet.exe build -c Release
.\bin\Release\net8.0-windows\bw-voice-signal-probe.exe <模式>
```

用固定的 dotnet8（跟桥同一套工具链）。系统 PATH 上的 `dotnet` 只有运行时没有 SDK。

| 模式 | 用途 |
|---|---|
| `--watch [秒]` | 连续采样**所有**候选信号，只打印变化。**配合人工制造一次已知状态变化**用 —— 这是验证探测器的唯一正确姿势，见下 |
| `--timing [秒]` | 100ms 高分辨率计时。量「按下 → 就绪」耗时；就绪的可观测标志是渲染侧出声（Codex 加载完成会「叮咚」一声） |
| `--diff [nopress]` | 触发前后各拍一次全量快照，列出**谁动了**。默认会自己按一次 F24；`nopress` 则只做对照 |
| `--hook` | 低层键盘钩子：判断注入的按键**到底有没有进入系统输入流**。区分"我们发的键被挡了"和"对方收到了不理" |
| （无参数） | 枚举音频会话，只打印变化 |

## 它读哪些信号

| 信号 | 结论 |
|---|---|
| 麦克风台账（`ConsentStore\microphone\OpenAI.CodexBeta_*` 的两个时间戳） | ✅ 可靠 —— 通话开始写 start、结束写 stop |
| WASAPI 音频会话状态（采集/渲染，per-pid） | ✅ 可靠 —— 随通话出现/消失 |
| 音频**峰值电平**（`IAudioMeterInformation`） | ✅ 最有信息量 —— 区分"流开着"和"真有声音"；渲染侧的尖峰就是就绪提示音 |
| 进程 TCP 连接 | ⚠ 会变但不专属语音 |
| 线程数 | ⚠ 噪声大，只作旁证 |

## ⚠ 用它之前必须先读这一段

**没有已知为真的状态变化，就没法验证探测器。**

那次排查我下过三次错误结论，全是同一个毛病：**拿"没观察到变化"当"什么都没发生"**。

| 我观察到 | 我当时的结论 | 实际 |
|---|---|---|
| 会话 Active 持续 45 秒不变 | "Codex 常驻占麦，这个信号没用" | 语音**当时就是开着的**，信号是对的 |
| 按下 F24，零变化 | "Codex 不响应快捷键" | 是**我注入的**按键不生效，桥自己发的有效 |
| 五路信号全零变化 | "我们没有任何可靠的程序化观测" | 三路都可靠，是我没做对照 |

每一条观察都有**两种解释**（信号瞎了 / 什么都没发生），而我每次都只挑了一种。
直到用户手动开关了一次语音 —— 一个**已知为真**的状态变化 —— 三个误判一次全被纠正。

所以正确姿势是：

1. 先开 `--watch`；
2. 让**人**去制造一次确定的状态变化（手动开/关语音，并告诉你他做了什么）；
3. 看哪一路跟着动了 —— 动了的那路才是可用信号；
4. 之后才谈得上用它去判断别的事。

`--diff` 自己按键的那个模式**不能**用来验证信号：按下去要是什么都没动，
你分不清是信号瞎了还是这次根本没打开。它只在信号已经验证过之后才有意义。

## 那次量到的数

```
台账 active=True（麦克风打开）→ 渲染侧出声（叮咚，就绪） = 2.25s / 2.18s（两次实测一致）
ReaderPC 启动 → 语音自动打开 = 3.9s，再 2.2s 就绪
```

这两个数直接决定了桥里的 `StartObservationTimeout` / `StartUsableSettleDelay`
（原来是 20s + 8s，在没有观测手段时拍的，比实际大了近一个数量级）。
要再调那两个常数，先用 `--timing` 重新量一遍。
