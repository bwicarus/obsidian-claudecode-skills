# 卡片输出

Windows Codex 语音中，原生天气、新闻、图片、视频或事实类工具得到结构化结果后，必须在同一轮
调用 `reader_card`，把结果镜像到当前快照精确指向的 App 或扩展。文字聊天历史同步只携带用户和
助手文字，不携带卡片；不得从最终回答文字反推或补造卡片。

## 调用外壳

输入只能有 `card` 一个字段；`card` 必填 `kind`、`title`、`data`，另有一个**可选**字段
`bind`（把卡片钉到页面上的某个元素，见下文「钉住内容」）：

```json
{
  "card": {
    "kind": "fact",
    "title": "标题",
    "data": { "answer": "结论", "detail": "补充" }
  }
}
```

- `kind` 只允许 `weather`、`news`、`images`、`videos`、`fact`、`general`。
- `title` 是必填字段，值为 `null` 或不超过 320 字符的字符串；空字符串也有效。
- 整个卡片 payload 的 UTF-8 编码不得超过 32 KiB，嵌套深度不得超过协议上限。
- 下文的 `text` 表示非空白、无 NUL、最多 2,000 字符的字符串；`scalar` 表示有限 JSON
  数字或符合 `text` 规则的字符串。标为可选的字段可以省略，但出现时不能为 `null`。
- 所有对象都拒绝未列出的字段和重复字段。`card` 的「已列出字段」包含可选的 `bind`。

## 钉住内容（`bind`）

不带 `bind` 的卡片是**浮层**：它跟着当前轮次走，轮次结束就消失。带 `bind` 的卡片
**钉在页面的某个位置上**：跟着那处内容滚动，闲置时收成一个小圆点而不是消失，
目标不在屏幕上时自动退回浮层。给某一处正文做讲解、纠错、补注时用它。

**不需要用户先选中。** 你自己读页面、自己挑那一段、自己绑上去 —— 要求用户先划选
不是常态。只有当用户明确说「就这段」时才用他的选区。

`bind` 是二选一的形状（也可以传 `null`，等同不带）：

```text
{ "kind": "upage-block", "upage": text, "bid": text }
```

钉到**用户插入页**里的某个块。`upage` 是插入页 ID，`bid` 是块 ID，都来自快照。

```text
{ "kind": "page-chars", "page": int≥1, "from": int≥0, "to": int≥0,
  "text"?: text, "rev"?: text }
```

钉到**书正文**的一段字符上。`from`/`to` 是该页字符层里的下标，闭区间，`to ≥ from`。

**序号从哪来**：调 `reader_page_text` 取该页文本，它返回的 `segments` 是
`[{from, to, text}]` —— 每项是一个词组及其字符区间。挑中你要讲的那几项，
`from` 取第一项的、`to` 取最后一项的。别自己数字符：空白在字符层里**占序号但不成段**，
手数必错位。

**最省事的方式：给块号 + 原文，序号不用自己算。**

正文每一行形如 `[NN] 这一块的文字`。看中哪句话，直接：

```json
{"kind":"page-chars", "page":12,
 "block":7, "text":"エネルギーは保存される"}
```

阅读器自己换算成字符区间。**不需要先调 `reader_page_text`，也不用拼 from/to。**
块把搜索范围锁住了 —— 所以同一句话在页内重复出现时也不会认错，
这正是它比只给 `text` 更准的地方。

⚠ `[NN]` 是**块地址不是字符下标**。它只用来说"第几块"；要下标仍然只能用 segments。

⚠⚠ **只填你在正文里真的看见的那个 `[NN]`，不要自己数行号。**
一页**只有一套**块编号，`[NN]`、`reader_page_text` 的 `segments[].block`、
阅读器解析时算的号，说的都是同一件事 —— 但前提是你抄的是它印出来的那个号。
自己数出来的行号跟它不是同一套：块内找不到 → 退回全页按文本找 →
同一句话在页内重复时会钉错地方。2026-09-04 实锤过一次：助手说第 11 块，
那页只有 8 块，卡片钉到了页内第一处一样的字上。

正文里没有 `[NN]` 就**别给 `block`**，只给 `text`。快照里的**数据表**
（`| 国家 | 特征 |` 那种）单元格内不印号 —— 每格都加编号会把表格毁掉；
要钉表格里的内容就调一次 `reader_page_text`，它按块折行，表格每一格
在那里都有自己的 `[NN]`（也有 `from`/`to`）。

⚠ 给了 `block` 却对不上、而那句话在页内**不止一处**时，阅读器**不会**替你猜 ——
它直接钉不上并回错，请改用 `segments` 的 `from`/`to` 重来。只有一处时照钉，
回执标 `by-text-block-missed`。

⚠ 块号是**位置不是身份**：换一份 OCR、页面重排之后同一个 `[03]` 可能指向别的内容。
所以务必**同时给 `text`** —— 块内找不到时，若那句话在页内**唯一**，阅读器会退回全页
按文本找并在回执的 `how` 里标 `by-text-block-missed` 告诉你块对不上了；
若页内有多处相同文字，它不猜，直接钉不上（见上一条）。

回执的 `how` 就是这次定位的质量：
`exact`（用了你给的序号）/ `by-block`（在你指的块里找到）/
`by-text`（没给块号，全页找）/ `by-text-block-missed`（给了块号但没在块里）。

---

**需要精确序号时 —— 按文字对，不按位置对。**
segments 每一项都自带 `text`，所以你**不需要任何"位置对照表"**：
在正文里读懂这页讲了什么、决定要钉哪句话，再到 segments 里找出
**文字拼起来正好是那句话的连续几项**。

    想钉：「エネルギーは保存される」
    segments: … {from:10,to:14,"エネルギー"} {from:15,to:15,"は"}
                {from:16,to:18,"保存"} {from:19,to:22,"される"}
    → from = 10（第一项的）, to = 22（最后一项的）

全程不需要知道任何一个字在 Markdown 里的偏移是多少。这也正是为什么不需要
anchor map —— 它解的是「Markdown 偏移 → 字符下标」，而你要的是
「这句话 → 哪段区间」，segments 每一项已经直接回答了。

如果当前快照把漫画或表格正文整理成 Markdown，那份 Markdown 是**排版投影**：
它自身的字符位置只是显示用的，**绝不能当成绑定下标**。要下标就调 `reader_page_text`，
它返回的 `segments` 才是原始 `pageChars` 的闭区间。

> 2026-08-23 起不再随正文内联 `reader-structured-anchor-map/1` 那张表。
> 它是为了省掉这一次工具调用，实测却占了页面正文的 41%；而且它并没有消除
> 「Markdown 位置」与「pageChars 下标」两个坐标系长得一样这个陷阱，
> 只是给陷阱附了一张对照表。序号的唯一来源就是 `reader_page_text`。

**普通网页同样可以钉**（2026-08-23 起）。用的是**同一个** `page-chars`，
不要去找什么"网页专用的锚"——没有那种东西。三点差别：

- `page` 恒为 **1**。网页没有分页，整篇就是一页。
- `from`/`to` 是**整页**（含导航、边栏）的字符下标，不是正文区的。
  取值方式不变：调 `reader_page_text`，用它给的 `segments`。
- 网页版 `reader_page_text` 的每条 segment 多带两个字段：
  `block`（块编号，与正文里的 `[NN]` 对应）和 `region`
  （`正文` / `边栏` / `导航` / `页眉` / `页脚` / `其它`）。
  **用它来判断该不该引用某段**——把导航栏的文字当正文讲是最常见的错。

页面变了（SPA 重渲染、广告插入）时下标会整体偏移，所以网页上 `text` 比在书里
更重要，见下条。

**尽量带上 `text`**：同一个词在一页里常出现好几次，文字层重跑（换 OCR 结果、
重新预处理）之后下标会变。阅读器会拿 `text` 加上原始下标就近重新定位，
把卡片放回正确的那一处；不带 `text` 就只能认下标，文字层一变就可能钉错地方。
`rev` 是文字层版本号，快照给了就带上。

区间不合法（`page < 1`、`from < 0`、`to < from`）会被整条拒收，不会静默丢弃 ——
与其在页面上定出一个荒唐的位置，不如让你立刻知道发错了。

带 `page-chars` 的卡片有稳定写入身份：同一本书的实时来源在线时，即使当前显示另一页也会
直接写入目标页；如果目标 App 暂时离线或退到后台导致来源断开，Direct 会返回 `queued` 并把
写入保存在本机，匹配的书重新在线后自动落库。看到 `queued` 就不要重复创建。浮层卡、导航和
高亮仍然是当前页面的即时操作，不进入后台队列。

## 各 kind 的完整 data schema

### `weather`

```text
{
  "lo": scalar,
  "hi": scalar,
  "cond": text,
  "loc"?: text,
  "date"?: text,
  "precip"?: scalar,
  "tip"?: text
}
```

`lo`、`hi`、`cond` 必填；其余字段可省略。

### `news`

```text
{
  "items": [
    { "t": text, "s"?: text, "src"?: text }
  ]
}
```

`items` 必须有 1–20 项；每项的 `t` 必填。

### `images`

```text
{
  "items": [
    { "url": https-url, "title"?: text, "aid"?: text, "src"?: text }
  ]
}
```

`items` 必须有 1–20 项；每项的 `url` 必填。

### `videos`

```text
{
  "items": [
    {
      "title": text,
      "thumb"?: https-url,
      "url"?: https-url,
      "channel"?: text,
      "src"?: text
    }
  ]
}
```

`items` 必须有 1–20 项；每项的 `title` 必填，`thumb` 和 `url` 均可省略。

### `fact`

```text
{ "answer": text, "detail"?: text }
```

`answer` 必填，`detail` 可省略。

### `general`

```text
{ "text"?: text }
```

`data` 可以是空对象；若提供 `text`，它必须符合上述文字限制。

## URL 与兼容边界

`https-url` 最多 2,000 字符，必须是带非空 host 的绝对 HTTPS URL；前后不能有空白，不能含
userinfo 或反斜杠。图片 `url` 及视频 `thumb`/`url` 受此规则约束；`src` 只是来源文字，不会
被当作 URL。只引用 Reader 能加载的 HTTPS 资源，不传本地路径、`data:` URL、脚本或 HTML。

兼容调用仍可使用：

```text
BWREADER/1 card {"card":{"kind":"fact","title":"标题","data":{"answer":"结论"}}}
```

新调用应优先使用 typed `reader_card`。若 Codex 客户端的 `enabled_tools` 白名单尚未暴露它，
可直接调用始终保留的 `reader_command`，并传入与上文完全相同的 `{ "card": ... }` typed
对象；不要把对象重新拼成自由文本。`reader_command` 也继续接受上述 `BWREADER/1 card ...`
兼容字符串。三条入口都复用现有 Realtime 卡片校验、精确 source 路由和实际渲染回执；卡片
进入当前轮次的既有容器，不创建另一套 UI，也不改变 Realtime 或 CLI 流程。
