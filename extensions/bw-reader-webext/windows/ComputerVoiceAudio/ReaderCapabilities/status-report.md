# 状态回报

外部程序有时会推来一条**状态查询**，开头是「状态查询（requestId: …，有效期 … 秒）」。

收到时只做一件事：**运行它给出的那行命令**，把你的判断作为参数传进去。

不要开启语音、不要发送快捷键、不要重试、不要为了回答而改变任何状态。
这条查询只要一个答复。

    python "%LOCALAPPDATA%\BWReader\voice_status_receipt.py" ^
      --request-id <原样填回查询里的 requestId> ^
      --task-status ready ^
      --voice-status <active|ended|unknown> ^
      --evidence "<你据以判断的依据>"

命令跑完会打印一行 JSON。看到 `"ok": true` 就算答复完成，不必再做别的。

## 三个字段

**`--request-id`**：把查询里的 requestId 原样填回。填错等于没答 ——
提问方按这个编号找答复。

**`--task-status`**：
- `ready` —— 你收到并处理了这次查询。
- `error` —— 你收到了但没法处理（比如命令跑不起来）。

⚠ `ready` 只说明**这条任务在正常处理消息**。它不代表音频设备、麦克风或语音
连接已经就绪 —— 那是另一回事，别用 `ready` 去暗示它。

**`--voice-status`**：
- `active` —— 系统当前标记语音为已激活。
- `ended` —— 系统当前标记语音已结束。
- `unknown` —— 没有足够新鲜的证据。

⚠ `active` 只是**系统的标记**，不保证麦克风、扬声器、音频传输都正常。
⚠ **没收到语音消息不能推断成 `ended`。** 没有消息只是没有消息。
拿不准就填 `unknown` —— 填 `unknown` 永远比猜一个具体值有用。

**`--evidence`**：一句话说明你是凭什么判断的。例如
「系统语音模式标记为已激活」「刚收到一条实时语音消息」
「刚调用 end_realtime_voice_call，返回 ended=true」。

## 时间：不知道就别填

命令还接受一个可选的 `--observed-at <ISO8601>`，意思是**你看到那条证据的时刻**。

**知道才填，不知道就别加这个参数。** 脚本会把它留空。

⚠ 千万别拿"现在"去填它。答复的时间脚本自己会记；`--observed-at` 记的是
证据本身多新。这两个混在一起，提问方就会把五分钟前的观察当成刚刚的观察，
然后据此做出错误的判断。留空是**有用的信息**，假的时间戳不是。

## 前一步做过什么，就把它当证据

如果这次查询紧跟在一次挂断请求之后，而你刚调用过 `end_realtime_voice_call`，
把那次调用的返回写进 `--evidence`（例如 `ended=true`）——
那是最直接的一手证据，比任何推断都可靠。

## 查询过期了怎么办

查询带「有效期 N 秒」。超过就别再答了：迟到的答复描述的是另一个时刻的状态，
而提问方已经按"没答上来"往下走了，这时再插一条只会让人以为那是当前状态。

## 判断依据一把抓（2026-08-30）

要判断「现在该不该说、怎么说」时（路由说"你来定"、或任何要掂量时机
的场合），**只跑这一条命令**：

```
python C:\Users\bwica\AppData\Local\BWReader\judgment_basis.py
```

一次拿到全部判断依据：地点（含新旧）、语音链路连没连（他现在听不听得
到你）、有没有活跃阅读、最近一通电话、复习积压、待办规模、有哪几台
摄像头。每一项自带新鲜度，「不知道」直说。

⚠ **不要自己去翻散落的文件拼这些依据** —— 那会花好几轮，而且你临场
拼的路径没人测过。这个工具就是为了让判断只花一轮。机器可读加 `--json`。

⚠ 它**只列**摄像头清单，永远不自动拍照 —— 要看现场仍然是你自己调
`reader_camera_snap` 当场拍一张（拍照是「按一下才拍一张」，不变）。
