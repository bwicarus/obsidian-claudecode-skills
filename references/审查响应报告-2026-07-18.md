## 一、5 项止血(全部核实为真 + 已修)

### #1 掌握度阈值虚高
- **问题**:`compute_level` 把 `mastery≥0.20` 判为 level 2,`level≥2` 即 `state="mastered"`——20% 掌握就显示绿色已掌握。实测 LADR 28 个 mastered 全部 mastery<0.8,其中 19 个非推断。技能树的 mastered/解锁/bottleneck 都不可信。
- **核实**:读 `link_and_mastery.py` 的 `if level>=2: state="mastered"` + `compute_level` 的 `m>=0.20→2`,实测节点掌握度确认。既有逻辑,非本轮引入。
- **修法**:拆分"解锁下游(level≥2 = 可作前置,不变)"与"绿色已掌握(mastery≥0.8)"——0.20~0.8 = 新增 **in_progress(青色·进行中)** 态;bottleneck 判定改用 `level≥2`;`open_set` 加 in_progress;删死代码 `mastered_set`。前端加 in_progress 渲染(CSS tile/theme/badge、detail 标签、edge 映射)。
- **验证**:重算 LADR → **mastered 28→0**(无假绿)、in_progress 22;前端 node --check 通过;部署 skilltree 200。
- **文件**:`scripts/kg/link_and_mastery.py`、`_server_deploy/templates/skilltree.html`。

### #2 诊断绕过"用户确认"(本轮我引入的)
- **问题**:A1 在 daily 里 `mastery = max(Anki, 诊断得分)` 直接改掌握度,没经 proposal/override 确认——违反"AI 提议、你确认"铁律。叠加 #1,1/4=0.25 也会变 mastered。
- **修法**:撤掉 A1 自动折叠;诊断结果**只存 `mastery_diag` 证据、不折进 mastery**;`has_own_notes` 也不再把诊断当"有掌握数据"。掌握度更新只走 proposal→确认→override。
- **文件**:`scripts/kg/link_and_mastery.py`。

### #3 融合权重 F1=1.0 = 标签泄漏
- **问题**:训练正例几乎全 D=1(词典命中)、负例几乎全 D=0(随机对),而 D 特征就是"词典命中"——模型只要照抄 D 就 F1=1.0。学出 D=4.70 一家独大,是循环论证不是泛化。
- **修法**:把"词典命中但向量远"的对(preface↔向量类)从丢弃改成 **D=1 的负例**(双确认)——负例里既有 D=1 又有 D=0,D 不能再靠抄标签分类。
- **验证**:重跑 fit:W 从 {T:0.24,S:1.34,O:1.55,**D:4.70**} → {T:0.64,**S:2.53,O:2.74**,D:2.43};F1 从假的 1.0 → 真实 **0.94**(holdout 0.936);S/O 升为主力(符合"向量最可靠")。
- **文件**:`scripts/attention_profile.py`。

### #4 daily 实际没跑(文档修正)
- **核实**:`server-config.daily.enabled=false`,`last_run.json` 01:00 = `skipped`。报告原写"明天自动跑"是错的。
- **修法**:报告改正 + 全局标 DISABLED;"自动跑"改为"修完数据模型后手动开 + 先 dry-run"。

### #5 read_material 路径越界(安全漏洞)
- **问题**:`Path(VAULT_ROOT) / rest` 直接拼,`rest` 来自模型参数、无校验;`note:/etc/passwd` 可读任意系统文件。
- **修法**:新增 `_safe_vault_path`(resolve 后必须在 vault 内 + 扩展名白名单),note/book 分支使用。
- **验证**:`note:/etc/passwd`、`../../.ssh/id_rsa`、`book:/etc/passwd#p1` 全被挡,正常笔记照读;部署重启,经 webapp 进程线上确认已挡。
- **文件**:`scripts/attention_profile.py`。

## 五、唯一剩下的:mention schema 迁移(设计已拟,未执行)

审查 #6 里没做的三样本质上都要 events.db 的 mention 模型(每个 mention 带 span/lang/method/confidence/parent):
1. **多次独立出现计数**——打分现在仍 `set(terms)` 只算一次(dedup 保住了词、但没按次数加权)。
2. **lang 驱动的日→中语义归一**——concepts 现全 ASCII(英→中),日→中没真建立。
3. 少量 UI 噪声(全問未回答 类)。

**设计**:`extract_mentions()` 产出带元数据的 mention + 保留 `extract_terms` 薄封装(旧调用不破)→ 打分按 mention 计数 + 父子降权 → lang 由 method 派生 → bump 抽取器全量重抽(events.db 是派生索引,零数据迁移)。风险集中在打分改动 + 全量重抽,建议单独一轮分步执行 + 每步 dry-run 对账。
