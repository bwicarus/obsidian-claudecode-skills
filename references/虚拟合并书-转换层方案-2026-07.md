# 虚拟合并书:问题复盘与转换层方案(2026-07-19,供外部审查)

> 功能定义(用户设计):同名+partN 的分卷文件在系统里视作一本书——书架一条、页码连续(part1 有 x 页
> 则 part2 第 1 页显示为 x+1)、滚动跨卷零等待、AI/概念网/技能树把它当一本书;原文件不动,纯虚拟层。
> 命名助手:重命名输入与已存在书同名 → 自动建议 partN+1(可改)。

## 二、失败复盘:bolt-on 特例路线(已废弃并闸掉)

阅读器侧我走了"在旧架构旁边挂特例"的路线,四轮补丁每轮修一个问题又冒出新的:

| 轮 | 做法 | 暴露的问题 |
|---|---|---|
| 1 | 显示偏移叠加(_dispPage+组偏移)+ 边界浮标按钮 | 「加载中」占位页码与顶栏不一致(3处没走偏移);浮标在连续滚动模式不出现(该模式绕过挂钩子的函数直改 DOM) |
| 2 | 滚动越界自动跳卷(wheel/touch 累积阈值) | touchmove 里每次读 scrollHeight 强制重排 → 严重卡顿;跳卷落地被本地旧续读仲裁拽回(深链 ts=0 必输) |
| 3 | 回流修复(rAF 边缘标志)+ 深链必胜 + 武装/驻留防乒乓 | 翻回上一卷仍卡(落地即在底部边缘,回弹又触发=乒乓) |
| 4 | 盒子模型 bolt-on(外卷页盒子接在末尾+停稳换会话) | **单页/双页等模式大量异常**——这些模式的内部逻辑(页判定/滚动条/跳页钳制/spread 行/插入页/内存卸载)都不知道"外卷盒子"的存在 |

**根因(不是哪个补丁写错,是路线错)**:每一层功能都被要求"知道分卷的存在",而阅读器有 100+ 处
页码/文件语义(下节实测 114 个 API 端点、31 个前端模块)——特例打不完。这违反了本项目自己的
统一控制层铁律:"让中间层去适应旧代码,不为新形态另造上层建筑"。

**当前止血状态**:`__GRP` 默认 null(全部组行为 no-op),阅读器行为=合并功能之前;`&vmerge=1` 保留实验入口。
第一节那些不经过阅读器内部的件全部保留。

## 三、转换层方案(提议,待审查)

### 原则

**程序其余部分零改动。分卷只在两个咽喉处被翻译掉,其余代码(全部 31 个前端模块、全部功能)
永远只看见"一本 135 页的书"。**

### 咽喉 1:文档门面(客户端唯一改动点)

阅读器的世界只依赖三样:`pdfDoc`(numPages/getPage(n))、`FILE_REL`、发往服务端的 `(file,page)`。
- 合并态打开:`?file=<canonical>&merged=1`;
- `pdfDoc` = **合并门面对象**:`numPages=135`;`getPage(60)` → 懒加载 part2 的真 PDF.js 文档 → 返回其第 5 页。
  PDF.js 页对象自带渲染上下文,单页/双页/连续/缩放/滚动/文本层**全部照常**——它们只跟 pdfDoc 说话。
- **先例**:图片模式已经用同样的 pdfDoc shim 让全部代码无感知运行(03-loader:"其余代码靠 shim 的
  getPage().getViewport() 照常工作")。本方案是同一模式的第二个实例,不是新发明。
- `FILE_REL` = canonical;客户端内部页码**直接就是全局页**(v1 的全部显示偏移 hack 删除,不再有两套页码)。
- 各成员的 PDF 字节按需经现有 pdf_url 通道加载(range 支持已有);滚动到外卷区时才拉那卷 → 天然满足
  "滚动零等待+渐进加载"(占位盒子机制阅读器本来就有)。

### 咽喉 2:服务端 (file,page) 翻译(存储不变式的唯一保证点)

客户端继续盲传 `FILE_REL+page`(零改动)。服务端在 `/pdf/api/*` 入口统一翻译:
- 识别:`file=<canonical>` 且请求带 `merged=1`(客户端 fetch 不改——由模板给 `__PDF_CFG.file_rel`
  直接放入带标记的虚拟 rel,如 `canonical` + cfg.merged 标志,由**一个**既有的 URL 构造点追加;
  具体注入点实施时定,原则是客户端仍然只有一处知道)。
- 翻译:`(canonical, 全局60)` → `(料理师part2.pdf, 局部5)` → 交原 handler。
- **不变式**:所有 sidecar/缓存/埋点永远存**真文件+局部页**(由咽喉保证,不再依赖每个功能自觉);
  合并只是视图。已有的每卷高亮/便签/墨迹零迁移、在合并视图自动正确出现。

### 端点翻译清单(实测枚举,114 个)

- **45 个逐页端点(file+page)= 纯透传翻译**:page-image/page-chars/page-text/page-translate/
  highlights(单页)/ink/dict 系/translate/figures/userpages/insert-page/dwell 埋点等。
  翻译进(含 POST body 里的 page),响应原样(它们只关于翻译后的那一页)。
- **44 个整本级端点(只 file)分三类**:
  a. **列表扇入**(合并视图要看到全组):GET highlights(整本)/notes 列表/book-figures/目录 toc/
     书内搜索 /api/search、vocab-mastery-map 等 → 对每个成员调原逻辑,页码+offset 合并返回;
  b. **真·按卷操作**(不该合并):压缩/预处理/预热/删除/重命名/上传 → 作用于**真实成员文件**,
     合并态下 UI 语义=作用于当前所在卷(或明确列出成员);
  c. **EPUB 专属/与页无关**:不受影响。
- 剩余 25 个不带 file 的端点不受影响。

### 分阶段实施与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 | 端点清单逐个核对分类(上表是机器初分,人工过一遍 45+44) | 清单签字 |
| 1 | 服务端翻译模块(纯函数+单元测试:全局↔局部/越界/非组直通)+ 咽喉挂载 | 测试全绿;非合并请求零行为变化(回归) |
| 2 | 客户端 pdfDoc 门面 + merged 打开链路;先只验读路径:全模式滚动/跳页/选词/查词/翻译跨卷 | 手测清单:单页/双页/连续×跨卷边界 |
| 3 | 列表扇入端点(a 类逐个) + 写路径全量(高亮/便签/墨迹跨卷落真文件) | 每端点:合并视图操作→检查落盘在正确成员 sidecar |
| 4 | 位置(canonical+全局页,与既有 per-part 记录仲裁)/书架入口切 merged/清理 v1 残留 hack | 两晚真实使用 |

### 风险与开放问题(请审查者重点看)

1. **虚拟 rel 的泄漏面**:merged 态的 canonical/全局页会不会流进翻译层覆盖不到的通道——
   SSE 总线 ctx、assistant/语音的 file 参数、MCP 工具、注意力埋点(埋点必须记真 rel,否则概念网
   /画像数据被污染)。计划:翻译层挂在 bp 入口,上述通道全走 /pdf/api → 应被覆盖,但需逐通道核实。
2. **列表扇入清单完整性**:44 个整本级端点的 a/b 分类是机器初分,漏一个=合并视图缺一块数据。
3. **PDF.js 多文档内存**:两个(将来更多)成员文档同时打开;计划 LRU 只保近 2 个成员 doc,远卷销毁。
4. **spread(双页)跨卷行**:全局第 55/56 页会被排进同一行(分属两文件)——门面 getPage 天然支持,
   但需确认 spread 行构造只用 pdfDoc(初查是)。
5. **页码对齐(印刷页)语义**:per-卷特性;合并态下对齐输入应作用于"当前所在卷",UI 需说明。
6. **性能**:每请求一次组查表(内存缓存 O(1)),预期可忽略;需在阶段 1 实测。
7. **EPUB 分卷**:本方案只覆盖 PDF;EPUB 无页概念,暂只做书架折叠。
