## 0. App→Pi 同步范围（用户 2026-08-24 拍板，逐条）

> 起因：查实 **iPad App 上产生的高亮/便签/墨迹/插入页出不去**——
> 服务端连接收的接口都没有。而桌面之间其实不存在这个问题：
> 它们直接读写 Pi 上按账号存的同一份 sidecar（`by-user/<uid>/pdf-highlights/<sha1>.json`），
> 是**集中存储**，不是设备间同步。

| 域 | 同步？ | 时机 | 备注 |
|---|---|---|---|
| **高亮** | ✅ | **事件**：写入 / 取消时 | 用户原话「高亮写入或者取消时是需要事件同步的」 |
| **便签** | ✅ | 事件 | **内容和绑定都要**（anchor 已经是不透明信封，形状合适） |
| **插入页** | ✅ | 事件 | |
| **墨迹** | ✅ | **静置后**：一定时间不变动才同步 | 用户原话「不是实时而是一定时间不变动后同步」。记录粒度 = 一页的笔画，不是一笔 |
| 阅读进度 | ❌ | — | 用户明确不需要（也正好绕开「已有两套带 ts 仲裁的真源」那个前提） |
| 选中 | ❌ | — | 临时行为。⚠ **别跟高亮混为一谈** —— 选中是高频、临时；高亮是离散、持久 |

**机制**：走既有的同步网关（`sync-gateway/2`），不新造第二套。
理由是用户定的三条：**统一化**、**增量而非全量**、**独立更新而非打包**——
而网关本来就是记录级的 `{operation: put|remove, record}` + 游标定序 +
revision 显式冲突 + tombstone，正好全中。账本记录也自动就有
（`_ledger_sync_mutation` 已挂在那条路上）。

**已知的地基缺口**（下一轮从这里开始）：
1. 客户端注册表的 `isSyncCollection()` 要求 `scope === 'global'`，
   而这几个域都是 `scope: 'document'`；
2. App 建库时 `document` 库拿到的是 `causalCollections: []`
   （`native-local-runtime.js:579`）——文档作用域**结构性**地不参与因果同步；
3. ⚠ 但**服务端中继根本不在乎 scope**（全文只出现 1 次且不在判定里，
   它存的是不透明记录）。所以这条线是**客户端自己划的**，不是协议限制。
4. `document-notes` 缺 `recordSchema`；`provider: false` 也在判据里。
5. 高亮标着 `status: 'pending'`，原因写着「三种格式原 sidecar，不改写锚点」——
   **可能不构成阻塞**（同步不要求改写锚点，便签就是以不透明信封同步的），
   但**尚未验证**。

## 1. 要解决什么

一句话：**让「我什么时候、在哪个界面、看了什么、生成了什么」变成一条可查、
会自己变短、不会无限膨胀的记录。**

跟已有的 `attention-kb-design.md` 是**两层不同的东西**，容易混：

| | 回答什么 | 形态 | 现状 |
|---|---|---|---|
| 注意力**画像**（已落地） | 「我最近在关注哪些概念」 | 词/术语 × 衰减权重的排行 | `attention_profile.py`，每 15min 跑 |
| 活动**账本**（本文） | 「我什么时候在哪看了什么、生成了什么、它还在不在」 | 时序事件流 + 生成物台账 | 地基在，消费端和生命周期没有 |

画像是账本的一个下游消费者，不是替代品。

## 3. 真正需要新建的四件事

### 3.1 生成物生命周期（**最大的空白**）

现状：id 有两三套，**自动回收一套都没有**。全仓只有 6 处在做过期删除，
且全是「时长/数量硬上限」，**没有一处是按「是否被固定保存」判定的**：

| 现有的 6 处 | 规则 |
|---|---|
| 语音卡片回收站 | 1 天（唯一的软删除 + TTL） |
| 任务 run | 7 天（`RUN_TTL`） |
| 配方回收站 | 30 天 |
| 对话纯文本归档 | 180 天 |
| 语音录音 | 保留最近 400 段 |
| 插入页前的整书备份 | 保留 2 份 |

**完全没有任何清理的**：高亮 / 便签 / 插入页 / 收藏夹 / 墨迹 / 词组 /
实体编号注册表 / `vocab-lookups.jsonl` / `reader-review-events.jsonl` /
`voice-log/*.jsonl` / `anki/records/*.json` / KG 节点。

**「是否被固定保存」的判据不用发明** —— 实体注册表里已经有 `local` 字段
（是否已贴页并本地化；本地化时机就是「贴到页面时」而不是搜到就下）。
这天然就是「用户把它固定下来了」的信号。`asset-registry.md` 的 P3 待办里
自己就写着「未使用条目 TTL 清理」尚未做。

**方案**：给发号器加一个统一的 GC，判据三选一命中即保留：
- `local == true`（已贴页/本地化）
- 被任何一条持久记录引用（便签 / 高亮 / 笔记 / 卡片 / KG）
- 被用户显式「收藏/固定」

都不命中 → 到期进冷归档（见 §6），再到期才真删。

⚠ 两套 id 语法（`{kind3}_{hex6}` 和 `c_<hex>_<rand>`）今天还没统一，
`asset-registry.md` 的 P3 也列着这一条。GC 之前先合并，否则要写两份。

### 3.2 修改/删除的版本记录

现状：只有卡片改写留了完整版本历史（`_refresh.history`），配方有版本历史（保留 10）。
其它一律没有。

**方案**：不给每类生成物各造一套。走账本 —— 修改/删除各写一条 `channel=mutate`
的事件，`extra` 里带 `{op, target_id, before_hash, diff}`。原值进冷归档，
按 §6 的时限清。这样「版本记录」和「删除后保留期」是同一套机制。

### 3.3 「界面」维度

现状：**只有 `/api/active-reading` 的 `kind`（pdf|epub|html|web）一处是真的。**

⚠ 更要紧的一层：**「App / 桌面网页 / 浏览器扩展」这个区分今天在任何记录里都还原不出来。**
同一条 dwell，App 打来的和桌面打来的落盘后长得一模一样；扩展查的词和 App 里查的词
只有 `web:` 前缀这一点间接线索。

**服务端补不出来，必须在客户端上报时带 `surface` 标记** —— 三份 runtime 各改一处
（这是一个新的多副本契约，动手前登记进 `contract-sites.json`）。

### 3.4 「地点」维度

现状：**零基础设施。** 全仓 grep `geolocation` / `CLLocationManager` /
`NSLocationWhenInUse` / `latitude` 零命中。

**建议先不做真定位**（要加 iOS 权限 + 授权流，成本和隐私面都不小），
退而求其次用「设备 + 网络」当粗粒度地点（哪台机 / 哪个 Wi-Fi），
按 `append_raw` 的 `extra` 字段进，**不要新开一列**。

## 4. 记录格式

沿用 `append_raw()` 的账本协议，只加两个字段，不另起一套：

```jsonc
{
  "v": 2,
  "ts": 1755840000,
  "channel": "read",              // 已有 11 种，新来源在这里加
  "actor": "user",                // user | ai | system
  "surface": "app",               // 【新】app | desktop | extension | pi
  "place": "home",                // 【新，可选】粗粒度，进 extra 也行
  "file": "book:LADR.pdf#p37",    // 统一 id 语法（_material_ref）
  "label": "LADR.pdf 第37页",      // 【关键】人话，写时顺手调 _material_label
  "page": 37,
  "focus": {"kind": "text", "…": "…"},
  "extra": {}
}
```

**`label` 是你那条「记录里不能只有 id」的落点。** 写记录时顺手调
`_material_label(ref)`（不读全文、很便宜），AI 读记录时就不必回查。
这条有血的教训支撑：`references/evidence-quality-lessons.md` 记的是同一类事故 ——
**采集不可重来，分析层能重写一百遍，当时没存对的救不回来**。
为省几十字节让未来的 AI 逐个查 id，是拿不可逆的采集成本换可逆的存储成本。

### 什么记、什么不记（你的第 3 条）

| 对象 | 聚焦时 | 生成时 | 删除时 |
|---|---|---|---|
| 书 / 网页（体量大） | **记**（带 label） | — | — |
| 生成物（比书小一级） | **不记**（点击查看不记） | **记** | **记**，保留期后连生成记录一起清 |
| Anki 卡片 | 不逐张记 | — | — |

Anki 那一路走 §5 的会话聚合，不进逐事件流。

## 5. Anki 会话总结

### 已有的同构实现：`learning_situations.py`

结构跟你描述几乎一一对应，**照抄即可**：

| 你说的 | 它怎么做 |
|---|---|
| 数量门槛 | `LAPSE_TRIGGER_N=3`、窗口 `LAPSE_WINDOW_D=45` 天 |
| 不逐卡记 | 窗内 `ease=1` 先按 cid 聚合，再按「知识点」二次聚合（concept 优先取 KG 节点名，取不到才用卡面抽词 top1） |
| AI 只总结一次 | `analyze()` 用轻档模型跑一次，写 `analyzed=True` 后不再重跑 |
| **防止循环判定后重复工作** | **证据水位**：`last_evidence[src]` 存该源的单调 id（Anki 用窗内 `MAX(revlog.id)`）。只有**超过水位的新证据**才触发或复发；旧证据既不复活已 resolved 的，也不刷新 active 的 `updated` |
| 删除后保留一段 | `resolve/archive` **只转状态 + 留档，永不删除** |

**证据水位比按次数计数稳得多**，而且正好就是你说的第 (b) 条
「最后一张目标卡片到现在积累了多少新记录」。

### 数据可得性（已实测）

- `revlog` 里有**每次复习**的毫秒时间戳 + ease + 耗时；调查中在本机副本上实跑验证过
  「窗口内复习次数 / 不同卡数 / 困难+再来数」三个数字都算得出来。
- 卡面文字两条路都通：`anki/records/*.json` 本地就有；`read_material('anki:<cid>')`
  只读查询，不依赖 AnkiConnect（Anki 没起来也能查）。

⚠ **「困难/再来」在仓库里有三套互相冲突的口径**（`ease=1` / `ease<=2` /
`lapses` 累计列），直接混用会算错。**动工第一件事是统一口径并写进契约测试。**

⚠ 踩过的坑（`learning_situations.py:153-156` 记着）：SQLite `HAVING lapses >= N`
会被解析成 `cards` 表自带的 `lapses` 全历史累计列，导致**时间窗失效**。
必须 `WHERE ease=1` 后 COUNT，再在 Python 侧聚合。

### 会话边界（你的第 (b) 条的另一半）

「复习期间提问、改卡、生成新卡，然后继续下一张」算**一次**学习。
判据不是时间间隔，而是「最后一张目标卡到现在是否积累了某个量的**新记录**」——
即用账本自己的条数当会话切分依据。这条跟证据水位是同一个机制的两种用法。

|---|---|
| `attention_profile.append_raw` | 账本 append-only，**永不删**，`--rebuild` 也重导它 |
| `voice_realtime_relay._vlog` | 写原始事实、**不做任何过滤** —— 焦点判定在读取聚合时执行，规则可随时进化重算（**写时过滤 = 信息永久丢失**） |
| `learning_situations` 文件头 | resolve/archive 只转状态 + 留档，**永不删除** |

现有的全部「压缩」都是**读时聚合**，源永远在。理由不是保守：
`EXTRACTOR_VER` 已经升过 10 次，每次都靠源重抽。

### 建议方案：冷归档，不是删除

**你要的效果全部拿到，代价只是一点磁盘：**

```
raw-events.jsonl   ← 热账本。总结生成后，被总结覆盖的那些行移走
    ↓ 移动（不是删除）
archive/2026-08.jsonl.zst  ← 冷归档，单独的、长得多的 TTL
```

- 热账本里**在完成节点插入总结行**（`channel=digest`，带 `covers: [起止 ts]`），
  原始行移出 —— 你要的「文件变短、AI 读起来便宜」达成。
- 冷归档保留期单独设（建议 ≥ 1 年），到期才真删。
- `--rebuild` 时冷归档一并重导 —— 现有的重算能力不被破坏。

**为什么值得这一点磁盘**：总结质量取决于**当时那个 CLI 调用的水平**。
这是不可逆操作里最不该赌的一项 —— 总结写坏了、口径改了、模型换了，
有冷归档就能重来一次，没有就永久损失。仓库里已有的几个批量 AI 任务
（`refresh_weak_cards --task quality`、`describe_figures_batch`）都是
保留原始数据、只追加结论，不是没有原因的。

估算：`raw-events.jsonl` 的量级参照 Rewind 实测 26MB/小时是全屏录制的数量级，
文本事件流比它小几个数量级，一年的冷归档压缩后应该在百 MB 级。

### 一条你可能想知道的历史

`references/ai-assistant-webapp-patterns.md:369` 记着：
「未做（**有依据地克制**）：用户提的『注意力时间线（查词/滚动/提问时序）』
价值边际递减 + **每事件吃 prompt 长度**，视口焦点已解决主要问题」。

你这次基本是把当时否掉的东西重提 —— 但加了两样当时没有的：**压缩机制**
（所以不再吃 prompt 长度）和**界面维度**。当时那条否决的前提正是你这次要解决的问题，
所以不矛盾。但方案落地时应当在那份文档里回一句，否则下一个读到它的人会以为在绕圈。

## 7. 触发限流：照抄这七种，别重新发明

仓库里最成熟的一块。七种**可以叠加**的独立手法：

1. **内容哈希 = 幂等键**。`note_state.is_unchanged(note, skill)` 存 sha256[:16]。
   ⚠ 哈希**刻意剥掉自动管理的部分**（frontmatter、「相关笔记」节），
   否则 AI 自己写回的东西会让哈希变、下次又重跑。**这个坑直接抄。**
2. **增量首跑播种基线**。`audit_kg --incremental` 第一次跑时把当前全部哈希写进基线
   并**跳过本轮**，以后只审变了的。不这么做，开启增量的那一夜等于全量。
3. **结果字段本身当幂等标记**。`describe_figures_batch` 只处理 `desc` 为空的条目，
   每页写一次 sidecar（断点续传）。⚠ 临时文件名要带 `os.getpid()` ——
   四个写入方共用 `<sha>.json.tmp` 曾互相覆盖写出半截 JSON。
4. **冷却期 + 处理次数 + delta 门槛**。`refresh_weak_cards`：30 天冷却 +
   `count>=1` 不再做 L1 + 升级 L2 要 `lapses - lapses_at >= N`（改写之后又失败了 N 次）。
5. **证据水位（单调 id）** —— 见 §5，最对口的一条。
6. **内容寻址缓存跨对象复用**。`figure_dedup` 用感知哈希，同图跨书只描述一次。
7. **轮转游标 + 跑完自动清零**。`rescan_rolling` 每晚 30 页滚动覆盖全书。

另有两层外闸：数量硬上限、实时配额 / 时间感知预算，以及 `server-config` 的
per-task `enabled` 开关（凌晨任务的三个 AI 步骤各有一个）。

## 8. 「刚发生的事不查账本」（你的第 7 条）

这条是对的，而且有现成先例：创造物库只把最近 6 条的 `#id brief · 相对时间`
注入系统提示，全文靠工具取回。

**落地方式**：账本查询工具加一个**时间下限**参数，并在工具说明里写明
「最近 N 分钟内的事请用你自己的上下文回答，不要查这个工具」。
⚠ 面向 AI 的说明**写反比没写更糟**（CLAUDE.md 里记着这条教训：
没写它可能去翻 schema，写反了它直接放弃）—— 这句话要写成「不要查」，
而不是含糊的「优先使用上下文」。

## 9. 落地顺序（建议）

| 阶段 | 做什么 | 为什么排这儿 |
|---|---|---|
| 0 | 统一「困难/再来」口径 + 契约测试 | 三套冲突口径，不统一后面全部算错 |
| 1 | `surface` 字段（三份 runtime 各一处）+ 登记契约 | 客户端不带，服务端永远补不出来；越早越好，因为**历史数据补不回来** |
| 2 | 账本加 `label`（写时调 `_material_label`） | 同上，采集不可重来 |
| 3 | 冷归档机制（先只做搬运，不做总结） | 压缩的前置；先让「移走」这条路可用可回滚 |
| 4 | Anki 会话总结（照搬 `learning_situations` 的形状） | 第一个真实消费者，验证整套 |
| 5 | 生成物 GC（两套 id 先合并） | 空白最大但不阻塞别的 |
| 6 | 版本记录（走 `channel=mutate`） | 依赖 3 的冷归档 |
| 7 | 地点（设备+网络粗粒度） | 价值最低、最容易先跳过 |

⚠ **1 和 2 要尽早**：它们是采集侧的，历史数据补不回来；
其余都是消费侧的，晚做只是晚，不会永久损失。
