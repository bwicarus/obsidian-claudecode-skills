# 静默失败：一条链路上的十处，以及它们各自的伪装

2026-08-05 到 08-06，"网页内容传到 Windows 快照"这一个功能查了一整天。
最终发现的病因不是十个不同的 bug —— 是**同一个选择重复了十次**：

> 出了状况就悄悄什么都不做。

于是每修好一处，下一处才露出来 —— 因为**前一处的沉默正好盖住了后一处**。
本文记录这十处、它们各自长什么样、以及由此定下的规则。
下一个功能落地时先读这里，比重走一遍便宜得多。

---

## 一、十处清单

按发现顺序，也大致是从下游到上游的顺序。

### 1. 故障记录被重启冲掉

`lastError` 只活在内存，而 `status.json` 每次更新都整份重写。
supervisor 一重启，证据就没了 —— 一晚上三次，唯一幸存的记录是用户拍的照片。

**修法**：另写 `runtime/computer-voice-direct.failures.jsonl`，**追加**而非替换，
放在状态文件**旁边**而不是里面。任何重写状态的动作都拿不走它。

### 2. `catch (_)` 吞掉真实异常

```js
} catch (_) {
    contextSyncEnabled = false;      // 出错 → 判定为"关闭"
    say("上下文同步设置不可用", "err");
}
```

异常对象被丢弃，只留一句笼统的话。是什么错、哪一行、什么原因，全没了。

**修法**：`catch (err)` 并把 `err` 报出去。捕获不等于可以不看。

### 3. 错误写进 `display:none` 的元素

上面那句 `say(...)` 写进 `#status`，而紧凑形态的 CSS 里
`#status { display: none }`。内嵌框正是紧凑形态 ——
**那条错误在 iPad 上永远不可能被看到**。

**修法**：错误的出口不能依赖当前视图形态。改走跨文档通道送到宿主显示。

### 4. "还不知道"被当成"用户关闭了"

```js
if (!preferenceKnown || !contextSyncEnabled) return;   // 未知 = 关闭
```

一个尚未读出的偏好，被当作用户明确关掉的偏好。于是用户去拨开关毫无作用 ——
**开关的值从来不是被查的那个东西**。

**修法**：`if (preferenceKnown && !contextSyncEnabled) return;`
只有明确读到 false 才停。未知就继续做该做的事。

### 5. 读错存储，把空值当答案

```
content.js 读:      chrome.storage.local["bwReaderExtensionPreferencesV2"]
rc-settings.js 写:  localStorage[RC.ctxSync.LS_KEY]
```

两个不同的存储、两个不同的键名。读回来永远是 `undefined`，折成 `false`。

**修法**：先确认写的一方到底写在哪。折成布尔之前，
把**原始值**打出来 —— `raw=undefined` 与 `raw=false` 是完全不同的两件事，
而它们折完一模一样。

### 6. 投递挂在别人的回调里

`deliverToFrame(snap)` 被放在 `finishStorage()` 内部 —— storage 写入成功后的回调。
于是所谓"绕开 storage 的直投"从未真正绕开：写入一停，投递连同它的日志一起沉默。

**修法**：号称不依赖某物的代码，要检查它是不是还挂在那个东西的成功路径上。
"我以为拆掉的依赖"是最难看见的依赖。

### 7. 开关按站点隔离

`RC.ctxSync` 把设置存在 `localStorage`，而 content script 里的 `localStorage`
**属于宿主站点** —— 每个域名各一份，互不相通。
所以同一版代码在 fisc.jp 上读到"开"、在 note.com 上读到"关"。

**修法**：跨站点要共享的状态必须放 `chrome.storage.local`（扩展级）。
镜像一份过去，其余站点从镜像读。

### 8. 空镜像静默 return（新写的代码里）

```js
preferenceFromMirror().then(function (mirrored) {
  if (mirrored === null) return;    // 镜像是空的 —— 一声不吭
  ...
});
```

全新安装后空镜像正是最可能的状态，而它和"读到 false"从外面看完全一样。

**这一处是修前七处的过程中新写出来的** —— 足见这个习惯多顽固。

**修法**：三种情形各说各的（空 / 成功 / 失败）。

### 9. 整段没有诊断出口

`call.js` 说的话都走 `note()` 到宿主自己的状态行，
而页面级探针只显示 content.js 那侧的行 —— **框内部的话传不出来**。
于是页面说"已投递"、桥说"什么都没收到"，中间没有任何东西能指出谁记错了。

**修法**：诊断通道必须能跨越进程/文档边界，并带上"是谁说的"。

### 10. 误导性错误：`Load failed`

`fetch` 报 `Load failed`，看起来像网络不通、像主机不可达。
真实原因是 **CORS 预检**：JSON body 让请求成为非简单请求，
浏览器先发 `OPTIONS`，而桥既没有 OPTIONS 路由也不返回 CORS 头 ——
**真正的请求根本没离开 Safari**，所以桥的日志一行都没有。

**修法**：跨源 POST 必须同时处理 `OPTIONS` 并回 `Access-Control-Allow-*`。

## 二、最贵的一个教训：用错客户端验证

我在 Windows 上用 **Python** 测过这个 POST 端点，亲眼看着快照被覆盖，
于是认定"桥这侧没问题，断点一定在扩展"。这个结论把方向带偏了整整几轮。

**脚本不发 CORS 预检，只有浏览器发。**
我用一个不具代表性的客户端验证了"通路可用"，那个结论从一开始就是空的。

> 验证一条路径时，用的客户端必须和真实调用方具备相同的约束。
> 否则你验证的是另一条路径。

## 三、由此定下的规则

### 规则 1：每个提前退出都要出声

任何 `return`、任何 `catch`，都必须留下一句"为什么"。
哪怕只是「跳过：内容未变」。

代价是几行字。收益是不必再烧一轮 TestFlight 去问它。

### 规则 2：折成布尔之前，先把原始值说出来

`raw=undefined` 和 `raw=false` 要的修法完全相反：
一个是读错了地方，一个是用户真的关了。折完就分不出来了。

### 规则 3：诊断通道不能穿过被测对象

今晚九次给同一条链路装眼睛，每次都是因为**上一处的沉默盖住了下一处**。
仪表不能接在被测物内部 —— 被测物一断，仪表也读不出数。

诊断要么走独立通道，要么直接写进用户看得见的地方（页面 DOM、独立日志文件）。

### 规则 4：新功能落地时，诊断出口必须已经在

用户的原话，也是这套东西的设计要求：

> "我认为新功能创建时都可以这样创建状态回报的渠道，
> 然后只要软件有一个总的显示位置和调试模式开关就好"

落地方式（`src/bw-probe.js`）：

| 要素 | 实现 |
|---|---|
| 统一回报渠道 | `__bwProbe.probe(where, text)`，跨页面/内嵌框，带来源标记 |
| 总显示位置 | 页面左下角浮层，`pointer-events:none`，不挡操作 |
| 调试开关 | 任意页面加 `?bwdebug=1` 开启、`?bwdebug=0` 关闭 |
| 默认状态 | **关**。不能给用户每天访问的页面都糊一层诊断 |
| 早期报告 | 设置读出前的报告排队保存，开启后按序补放 |

开关存 `chrome.storage.local` 而非 `localStorage` —— 后者按站点隔离，
会让同一个开关在每个域名下含义不同。这一条正是第 7 处失败的教训。

URL 参数是关键设计：**开关必须能在没有控制台、没有开发者工具的设备上打开**。
iPad 上唯一稳定可用的入口就是地址栏。

新功能接入方式：

```js
var P = window.__bwProbe;
if (P) P.probe("模块名", "发生了什么");
if (P) P.skip("模块名", "为什么提前返回");   // 规则 1 一行写完
```

不要"出问题再补"。这条规则的由来，是用户在第九次装眼睛之后说的：

> "你下次能不能直接给新功能加一个可视化报错接口，
> 出问题我就直接把报错拿过来了不用这样一个个加"

它第一次就还了本：接入统一通道的同一版里，正文提取有个
`Can't find variable: articleRoot`，当场显示在屏幕上。
在此之前，同样的错误只会表现为"快照又没更新"，然后再花一轮去猜。

### 规则 5：无控制台的设备上，沉默等于不可诊断

iPad 上没有 Web Inspector。`console.warn` 等于什么都没写。
面向这类设备的代码，错误必须走能被用户看见、能被截图的通道。

## 四、这条链路最终的样子

作为对照，修完之后它是这样的 —— 比修之前少掉一大半：

```
content.js 采集
  → runtime 固定操作交给受信 background（严格校验 sender 与 schema）
  → background 一次 POST /reader-context/snapshot（不建长连接、不握手、不保会话）
  → 桥覆盖快照，最后一发赢
```

**关键认识来自用户的一句话**：

> "所有数据都只是一个 post 就结束使命了不是么，只要能覆盖旧快照就行"

在此之前，上下文一直跑在语音那套长连接机制上（WebSocket、hello、
context-open、会话 id、重连退避）。那些是为**让一段对话跨时间存活**设计的，
而一页的上下文用一次就作废。

代价不在复杂度，而在**够不够得着**：socket 必须由活着的文档持有，
而 iOS 上每种扩展文档都短命（background 被回收、popup 一关即毁、
内嵌框随页面而亡）。于是"哪个文档能扛住这条连接"成了一整晚的中心难题。

对 POST 来说这根本不是问题：内容脚本只需在发送的那一瞬间唤醒后台。

后续加入按需视觉与页面控制时又补了一条安全规则：宿主网页不能作为业务 relay。
iframe 的一次性 capability 只投给扩展亲手创建的精确 `contentWindow`；正文、图像请求、控制命令与
结果均走扩展 runtime，并绑定 `tabId + frameId + documentId + sourceInstanceId + revision`。

**当一个约束显得无解时，先回头问这个约束是不是自找的。**

## 四之二、2026-08-19 补：三种「读起来完全正确」的沉默

这一晚集中撞到三类，共同点是**代码本身挑不出毛病** —— 注释写得对、命名合理、
逻辑自洽，只是它从来没起过作用。这类比 `catch {}` 难发现得多，因为
review 时你会一路点头。

### ① 机制写好了，但那个变量从没被赋过值

`_armAuto` 里有一整个分支处理"绑定卡到点收成球而不是关掉"，注释还把设计意图
讲得很清楚。可全仓**没有任何地方给 `keepAsDot` 赋过值** —— 于是绑定卡照样消失，
而那段代码读起来完美无缺。

> **有分支就要有测试证明它进得去。** 只测"函数存在""分支存在"是不够的：
> 加一条断言，检查那个决定分支走向的值**真的会被写**。

### ② 拒绝式白名单只改了一边

给页数据加了 `visionEffectiveDpi` 字段，忘了在服务端 `_normalize_pc_page` 的
白名单里放行。那个白名单是 `set(page) - allowed` 非空即拒 —— 于是 PC 传上来的
**每一页**都被 400 拒，整本预处理 0/53 失败，UI 只显示"PC 预处理失败；可重试"，
重试多少次都一样。

> **拒绝式白名单是对的**（多出来的字段就是攻击面），但它意味着两边必须同步，
> 而同步靠人记是记不住的。做法：写一条测试，从生产端源码里 grep 出实际会发送的
> 字段，跟白名单做集合差。同理适用于"网页发的 action vs 原生认识的 action"。

### ③ fetch 对非 2xx 不会 reject

`rc-flashcard` 的卡片状态同步只有 `.catch()`，没有检查 `response.ok`。服务端返
500 时 fetch 正常 resolve，代码照常往下走，这次状态更新就这么没了 —— 比"只认
TypeError"漏得更彻底，因为连 catch 都不会跑。

> 每一个 `fetch(...).catch(...)` 都要问一句：**非 2xx 时这个 catch 会跑吗？**
> 答案永远是"不会"。

### 附带一条：失败分类不能图省事

把"服务端暂时不可用"也纳入可重投是对的，但第一版写成 `status >= 500` 就错了：
500 是**服务端内部出错、状态不明**（可能已经写了一半），重投有重复计分风险；
502/503/504 才是网关明确说"请求根本没被处理"。这个区别是被既有测试逼出来的 ——
它守的正是"500 时要把卡片放回队列"。

同一批里还犯过一次：把"拿不到状态码"当成可重投（`status === 0`），于是 409
业务拒绝会被当成离线。测试原话是
`an HTTP rejection is authoritative and must never masquerade as offline`。

> **拿不到判据时不要猜。** 猜"大概是网络问题"比明确报错更糟：它会让一个
> 服务端已经明确拒绝的请求被反复重投。

### 工具层面的一条

写契约测试时，`assert.doesNotMatch(SOURCE, /realtimeSave/)` 会被**注释里**提到
的同一个词命中；`indexOf(A) → indexOf(B)` 的切片在 B 定义于 A 之前时会静默返回
空串，于是断言变成对空字符串求值。两者都会让测试红得或绿得莫名其妙。

> 断言前先 `codeOnly()` 掉注释；取函数体用"从 `function 名(` 到下一个同缩进
> `function`"而不是两个 indexOf 相减。

## 五、追加：最难发现的一种沉默 —— **退回旧行为**（2026-08-20）

上面十处的形态都是「什么都不做」。这次词锚这条链上抓到的两个 bug 是另一种，
更难发现：**出了状况不是停下，而是悄悄退回一个看起来完全正常的旧行为**。

| 出了什么事 | 表现 | 为什么发现不了 |
|---|---|---|
| `from/to` 用了数组位置，而 `__charBoxes` 被按 baseline 重排过 | 按序号定位**从来没命中过**，一直靠文本回退兜着 | 文本回退大多数时候找得对，结果看着是对的 |
| 便签挂载跑在 `__charBoxes` 挂上之前 | 词锚必然 `no-char-layer` → 退回老浮层圆球 | 圆球本来就是老形态，看着像"这卡就是这样的" |

两条都不报错、不进日志、不触发任何断言。前一条藏了多久无从考证 ——
它写下来那天起就没生效过。

### 判据

**凡是有"兜底/回退/降级"路径的地方，都要问一句：主路径失败时我看得出来吗。**

回退本身是对的（用户宁可看到老样子，也不要卡片消失）。问题是回退**没有留痕**。
三种改法，按代价从低到高：

1. 回退时 `console.warn` 一句，带上原因（成本几乎为零，本次两处都补了）
2. 回退计数进诊断面板（规则 4 那套 `__bwProbe`）
3. 契约测试钉住**时序**而不只是代码存在 ——
   `assert.ok(iBoxes >= 0 && iRemount > iBoxes)` 这种。
   只断言"那行代码在"是不够的：本次的 bug 里，代码全都在，**顺序不对**。

### 另一条：文档里写的"够用"要当成待核实，不是结论

设计稿把 charBoxes 就绪回调记成「现在靠 `mountAll` 幂等重试兜着，够用」。
实测下来 **没有任何东西会在 charBoxes 之后再跑一次 `mountAll`** —— 那句"够用"
是写的时候顺手推断的，从没验证过，而它长得跟核实过的结论一模一样。

⚠ 自己写的设计文档尤其危险：核实过的条目和顺手推断的条目**混在同一份清单里，
排版完全一致**。往后凡是"够用/应该没问题/兜得住"这类措辞，一律当 ⬜ 待核实。

## 六、契约测试自己也会静默失效（2026-08-20，词锚复查的最大收获）

词锚那批改动我写了 11 条契约测试、每条都做过「破坏即红」的变异验证，1504 条
全绿，然后功能里仍然藏着一个**完全不工作**的特性。

出事的那条测试长这样：

```js
assert.match(NOTE, /_rebindWord\(g\.ctl, r0\.left \+ g\.shiftX \+ 4, .../);
```

它断言的是「重锚代码存在」。而重锚代码当时挂在 `onResizeTLUp()` 里 ——
**左上缩放手柄**的松手事件，而卡片便签的 `.rc-note-hascard .rc-note-rs-tl`
是 `display:none`，用户根本点不到。整段是死代码。测试绿，功能零。

### 判据：钉存在 vs 钉位置

| 断言的东西 | 抓得住 | 抓不住 |
|---|---|---|
| 「这行代码在」 | 被误删、被重构掉 | **挂错地方**、挂在走不到的分支里 |
| 「这行代码在 X 函数体内」 | 上面全部 + 挂错地方 | X 本身是不是活路径 |
| 「X 里的两个探测点是同一个表达式」 | 上面全部 + 两处漂移 | — |

改法是先切出目标函数体再断言，并让切不出来时**报错**而不是静默退化：

```js
const iDrop = NOTE.indexOf("function dropNote(ctl, rect0, dx, dy)");
const iNext = NOTE.indexOf("\n  function ", iDrop + 10);
assert.ok(iDrop >= 0 && iNext > iDrop, "dropNote 改名了？重锚可能又挂错地方");
assert.match(NOTE.slice(iDrop, iNext), /_rebindWord\(ctl, _lr\.left \+ 1, _lr\.top \+ 1\)/);
```

⚠ 同一份文件里另一条测试踩过配套的坑：`indexOf` 找不到时返回 **-1**，
`slice(a, -1)` 会切出**几乎整份文件**，于是「在某函数里」这个前提悄悄没了，
测试照常绿。凡是用 indexOf 切片，两个下标都要断言 `>= 0`。

### 变异验证也要变异对地方

我当时的变异是「把参数改掉」「把这行删掉」——它们都能让测试变红，所以我以为
测试是有效的。**真正该做的变异是「把这段代码搬到另一个函数里」**，那才是
实际发生的错误形态。变异验证只能证明测试对**你想到的那种破坏**敏感。

### 为什么单靠自查发现不了

这个错和回执那次（`work` 拼好了却在 `.then(function () {` 里被丢掉）是同一个
形态：**补在了看着合理、但不是活路径的地方**。自查时我读的是自己刚写的那段，
它本身没有任何问题 —— 问题在它的**上下文**，而上下文正是我当初选错的那个。
六个独立视角里有四个撞到了它，因为他们不带「我知道这里是对的」这个先验。

对抗式复查的正确用法也在这里：**不要问「有没有 bug」，要问「这个改动碰到的
每一类东西各自会怎么坏」**（时序 / 交互 / 状态 / 几何 / 一致性 / 降级），
再让每条发现被三个不同镜头独立验伪（代码事实 / 复现路径可达 / 是不是既有行为）。
33 条原始发现里 15 簇送验、10 簇存活 —— 三分之一是噪音，不过筛会淹掉真的。

## 七、桩给的是假信心（2026-08-23，第二章那条教训原样重演）

第二章「用错客户端验证」讲的是：拿 Python 去验证浏览器路径，脚本不发 CORS
预检，假阳性把方向带偏几轮。**这次是同一条，换了个外壳。**

我给普通网页新写了三个文件（字符层 / 卡片锚定 / 页文本），用一个手写的最小
DOM 桩测过，17 项断言全绿，9 处变异全红，就发了出去。随后让 14 个 agent
按四个维度审计、每条由两个不同视角独立证伪，**5 条 high 全部站得住**，
其中一条的验证者**在真 Chrome 里实测复现**。

桩为什么骗了我 —— 三条都很具体：

| 桩里的样子 | 真浏览器里的样子 | 后果 |
|---|---|---|
| 文本节点连 `nodeType` 都没设 | 选区边界**经常是元素节点**（Ctrl+A 给 `<body>`、三击选段给段落父元素） | 「锁定元素」对最常见的手势静默失效 |
| 页面块都是 `<p>` | 大量站点正文写在 `<div>` 里（x.com、多数 React 应用、Gmail） | 一个块都认不出，却返回 `ok:true` + 空 text，**对 AI 谎称"整页就这些"** |
| 桩里 `document.head` 只是个空壳 | `window.__bwHead` 恒为影子树内节点 | `::highlight` 规则注进影子树，正文上**一个像素都不画**，而所有返回值都说成功 |

还有两条是"我自己写的警告没管住自己"：我在注释里写了**「标记不能往正文流里
插 DOM」**，却只想到了自己的标记 —— 扩展自己的振假名往正文塞 `<rt>` 读音、
译页把译文 append 进**同一个 `<p>` 内部**。开一次「あ」或「译页」，
此前钉的每一张卡当场连按文本都找不回来。桩里没有这些功能，所以测不出来。

### 由此加的一条规则

> **凡是跑在浏览器里的东西，桩只用来测算术，不用来断言"能用"。**
> 桩越像真 DOM，它给的信心越危险 —— 因为它会让你以为覆盖到了。

落地做法：

1. 桩要**有结构**（`nodeType` / 父子链 / `comparePoint`），否则整类情况零覆盖
   而你不会察觉；
2. 但桩**不能替代真机**。浏览器里的能力必须有一份用**真手势**打**真扩展**的
   回归：`extensions/bw-reader-webext/test_web_bind_local.py`
   （真三击、真 Ctrl+A、纯 div 站点、影子树样式落点、振假名、译页）；
3. 真机测试必须**挂进 `handoff_check.py` 的清单**——没人跑的测试等于不存在；
4. 真机跑出来的红，**先分清是代码错还是断言错**。这次两条红里恰好一条一个：
   `<nav>` 文字不属于任何块是**代码错**（AI 根本看不见它）；
   全选断言写死 `from === 0` 是**测试错**（层首是 HTML 缩进空白，
   Ctrl+A 规范化到第一个可见字符，真机 `from=3`）。

### 顺带一条：指标不能永远不达标

给页文本加了 `coverage`（块盖住了多少字符层）之后，真机实测 0.89 ——
差的全是块间 HTML 缩进换行。**一个永远不到 1 的指标，真出问题时也没人会
注意到**，等于没有。改成只算非空白字符后它才真能报出"有正文块被静默丢掉"。
