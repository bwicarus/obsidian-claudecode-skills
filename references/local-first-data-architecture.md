# 本地优先数据架构（讨论中，2026-08-14）

> 状态：**讨论进行中**。下面分「已定」和「未定」两部分，未定的不要当结论用。
> 起因：方向确认为「电脑上的 AI 通过工具和 MCP 做大量处理与文件管理」，
> 而现有 App / Pi / 桥接都还是按「App 内嵌助手」的形状建的。

---

## 一、已定的决策

### 1. 控制平面与数据平面分开

同一条 RPC 通道现在跑着两种性质完全不同的东西，其中一种用错了模式。

| | 例子 | 走哪 |
|---|---|---|
| **控制** | 翻页、画高亮、显示卡片、写便签 | RPC 打前端。前端不在线就明确失败 |
| **数据** | 读全部高亮、全书搜索、批量整理 | **读本地副本**，不过网、不依赖 iPad 醒着 |

判据：需要作用在「用户此刻看着的那个界面」上的，是控制；只是要读积累下来的内容的，是数据。

**推论**：MCP 工具层不该依赖语音链路。现在查询走
`MCP → 命名管道 → 桥接 → WSS → App`，前提是 App 正连着桥接；一旦换成官方
手机直连，这条链没了工具全废。数据走本地副本就没有这个依赖。

### 2. 快照推「状态」，积累的内容存「本地」

- **状态**（在哪本书、第几页、选了什么、笔落在哪）：只存在于前端，别处没有，
  必须每次为真，极小 → 实时推
- **积累的内容**（全部高亮、全部笔记、书库、卡片、KG）：电脑上应该本地就有一份
  → 同步，不是查询

⚠ **但「当前页正文」不属于要移走的内容 —— 见第 15 条。**
判据不是「状态 vs 内容」这么简单，而是**带上它省的往返，值不值它占的 token**。

> **两处事实更正（2026-08-14）**：
> - 一度以为快照带 256K 字符正文 —— 那是 `ReaderDocumentCorpus.MaximumTextCharacters`，
>   **浏览器扩展**整页网页的上限。App 阅读器每页正文上限是
>   `reader_outgoing_context.PAGE_TEXT_LIMIT = 4000` 字符（约 1200 tokens）。
>   别再按 256K 做决策。
> - 据此曾建议「把正文移出快照」，**已撤回**：省 1200 tokens 换一次模型往返
>   （1–5 秒）是净亏，与第 13 条否掉 progressive disclosure 是同一个道理。

### 3. 同步传事件，不传状态

状态同步在双向场景下必然要问「谁覆盖谁」，而这个问题没有正确答案 ——
两边都是真的，挑一个另一边就悄悄没了。

事件流：追加、幂等、按时间排序、重放得到状态。冲突从「选一个」变成
「都留下，按规则解释」。

**已有的一半**：`command-outbox/2`、`mut-v2-<32hex>` mutationId、`sync-batch`
本来就是事件队列。缺的是**下行分发**和**多端合并**。

### 4. 冲突策略按数据类型分，不能统一

| 数据 | 策略 | 为什么 |
|---|---|---|
| 高亮 / 便签（新增） | 直接合并 | 各加各的，几乎不冲突 |
| 阅读位置 | 最后写入胜 | 语义上就该是最新那个 |
| 便签正文 | 保留双方 + 标记 | 文本不能自动合并 |
| 掌握度 | **合并证据再重算** | 覆盖等于丢掉一次真实的复习 |
| Anki 调度状态 | **不同步**，只上传答题事件 | 见第 8 条 |

定一个全局 LWW 然后在掌握度上悄悄丢东西，是这里最容易犯的错。

### 5. 本地副本必须知道自己滞后多少

每份副本要带：**最后同步成功时刻**、**本地未上行的变更数**、**能否连上持久节点**。
工具返回时一并带出。

> 不知道滞后多少的数据，比明确过时的数据更危险 —— 前者让 AI 拿着陈旧信息
> 下断言，而且很自信。

### 6. 端的角色

```
        App（iPad）                    Windows
        本地副本 + 事件队列            本地副本(全量) + 事件队列
        订阅：当前书                   订阅：全部
             │  ↑                          │  ↑
        下行 │  │ 上行                下行 │  │ 上行
             ↓  │                          ↓  │
        ┌────────────────────────────────────────┐
        │  Pi ——— 持久节点（永不关机）             │
        │  · 事件日志（真相）· 定期压快照           │
        │  · 按订阅分发   · 备份                   │
        └────────────────────────────────────────┘
                    ↕（外部权威，不参与我们的同步）
              Obsidian Sync        AnkiWeb
```

- **每端只订阅自己需要的子集**：App 不需要全部书的 KG，Windows 需要（要批量处理）
- 事件流 + 定期快照：老事件压成快照，新端先拉快照再追增量。快照由 Pi 生成
- Obsidian / Anki 画在外面，因为它们有自己的同步，**我们只在各端读它们的本地副本**

### 7. 掌握度：乐观本地值 + 权威重算 ⭐

**这条是 2026-08-14 讨论后拍板的。**

掌握度是**算出来的**（图 × 证据流），不是存的，所以「谁算」是个真问题。

- 只有 Pi 算 → 离线复习时屏幕上的掌握度纹丝不动，要等联网、上传、重算、拉回
- 各端各自算 → 离线即时更新，但要求**所有端算法严格一致**

后者在本项目特别难：改一条规则（比如解锁阈值 50%→70%），Pi 和 Windows 几分钟
就更新了，**iOS App 要走 GitHub Actions 编译 + 手动装，可能滞后几天**。这期间
同一个知识点 iPad 说已解锁、电脑说没有，数据完全正确、两边都没 bug，只是跑着
两个版本的算法 —— 这种分叉极难查，会先去怀疑同步。

**采用折中**：

- 本地算一个**预览值**立刻显示（离线也能即时反馈）
- Pi 算的是**权威值**，同步回来后覆盖预览值
- 显示上区分（预览值淡一点 / 带待确认记号）

代价只剩「两端算法差太多时数字会跳一下」。这个降级很值钱：
**把一个正确性问题变成了体验问题** —— 前者悄悄给错结论，后者一眼看得见。

> 同一模式项目里已有先例：PDF 阅读器标生词的
> `_dropVocabUnderlineOptimistic`（乐观去下划线，不等服务器）。

### 8. Obsidian 与 Anki 是外部权威，只做投影不做副本

- **Obsidian**：vault 是文件系统，Obsidian Sync 管同步。写笔记 = 写文件，
  交给 Sync 传播。**绝不在 App 里另建一份笔记副本再同步** —— 那就是三方写同一份数据
  - ⚠ 单文件 200MB 上限，超了**不报错、就是不传**。任何往 vault 写文件的工具
    都要写完确认尺寸并出声（已有旁路 `push_big_files_to_pc.py` 是同一个坑）
- **Anki**：FSRS 状态有历史，两个调度器改同一张卡，AnkiWeb sync 只保留一边，
  另一边的复习记录**直接消失且不报错**
  - App 侧**只采集答题事件**（何时被答成 again/hard/good/easy），调度永远由 Anki 算
  - 事件流合并可解；状态双向合并在有记忆的调度器面前不可解

### 9. KG 分四层，依赖单向

| 层 | 是什么 | 跟人有关 | 成本 |
|---|---|---|---|
| **1 图** | AI 全文扫描出的节点 + 顺序 + 包含 + 前置 | **无关** | 贵，一次性，可增量 |
| **2 证据** | Anki 复习、答题、阅读时长、查词、高亮 | 相关 | 廉价，持续追加 |
| **3 掌握度** | 证据投影到节点 + 沿前置传播 | 相关 | 计算，非存储 |
| **4 应用** | 复习模式分析、诊断卷、路径推荐 | 相关 | 按需 |

**「图跟人无关」的推论**：可预先构建、可跨设备共享、**只读单向分发**（不需要
双向同步）、眼镜等新载体可直接复用已建好的图。

**一处必须解决的循环依赖**：现在 `link_with_ai` 的关联校验（节点 locked 且
前置 <50% mastered 就拒绝，写 `_rejected_links`）让第 1 层依赖了第 3 层。
该规则本质是**呈现策略（第 4 层）**，应改为**查询时按掌握度过滤**，而不是
写入时拒绝。好处：依赖恢复单向；用户后来学到了，历史关联自动可见。

**存储要拆**：`knowledge_graph/<book>.json` 现在图和 `_rejected_links`/掌握度
混在一个文件里 → 拆成 `<book>.json`（图，只读单向）+ `<book>.mastery.json`
（可写双向）。不拆的话图要白白承担双向冲突风险。

### 10. 跨源节点：需要「基准」，可以是指定的一本书

不做全局唯一节点，做**双层多对一**：

```
概念层（跨 source）        导数的定义
                          ↑        ↑
节点层（per-source）   甲-12    乙-8
```

- per-source 图保留（自洽、可验证、易调试），没对齐就退化成 per-source，不会坏
- 对齐**可撤销**：错了撤一条链接，不用重建图
- 掌握度记在概念层，证据仍挂节点层（在哪本书哪一页学的不能丢）

**规则：跨源合并需要一个锚。锚可以是外部权威，也可以是指定的某一本书。**
没有锚的，不跨。

**按「所指是否唯一」分四类**（不是按记忆型/逻辑型 —— 记忆型里也有会走样的，
逻辑型里也有绝对不走样的）：

| 类 | 内容 | 跨源 |
|---|---|---|
| **A** | 命名实体、正式定义与定理、常量、词汇字符 | ✅ 风险最低，多有现成 ID 可挂 |
| **B** | 语法点、逻辑方法、算法技能 | ✅ **必须带限定域**（`en:passive-voice` ≠ `ja:受身`） |
| **C** | 框架 / 诠释类（"为什么有季节"、理论视角） | ❌ 不同教材是不同框架，甲会了不代表乙会了 |
| **D** | source 内在的（本书记号、本课约定） | ❌ 天然 per-source |

**三条可机器判定的判据**：
1. 有没有外部锚点（Wikidata / 词典 / Unicode / 标准命名）→ A 类
2. **能不能出客观题** —— 能用对错分明的题验证的就能跨源，因为验证标准统一。
   与 `make_diagnostic`（选择题、客观判分）同一套判据，两处复用
3. 名字含指示词（本章 / 上述 / 这里的）→ D 类，锁死

**最本质的判据**：只有当「在 A 处掌握」能安全推出「在 B 处也掌握」时才合并。

**假合并 vs 假分裂不对称**：假分裂只是没享受到好处；假合并会让系统**自信地
说「你会了」**，污染掌握度进而污染复习计划。所以第一版**只对齐 A 类**。

**事后发现假合并**：某跨源节点在某个 source 下错误率显著高于其它 source
→ 标记可疑合并，提示复核（`error_patterns` 已有类似信号）。

### 11. 语法点属于 C 类，用基准书解决

不同教材对语法「解释不同但各自成体系」—— 是**不同的切分方式**，不是同一对象的
不同名字（日语：学校文法 未然形+助動詞 vs 教育文法 ない形；五段/一段 vs グループ1/2/3）。
名字相似度高，AI 大概率会合并，但语义不同 —— 最隐蔽的假合并。

**英语基准 = `资源/books/EGIU/EGIU-5e.pdf`**（English Grammar in Use 5e）：

- 每个 unit 天然是一个节点，切分是作者做好的，不用 AI 猜粒度
- 右页练习就是客观题，自带第 2 条判据的验证
- 术语国际通用，别的教材往它映射最容易

> `_server_deploy/grammar-nodes.json` 那 25 个节点的 title 自己写着
> 「demo，后续可换权威书的 KG 替代」—— 扁平、无前置关系、无溯源，
> 只是占位物。将来映射到 EGIU 节点上即可。

**基准机制的额外好处：让概念层可验证。** AI 抽象出的「仮定形」只存在于模型的
理解里，没法查、没法争论；「《EGIU》Unit 12」可以翻开看。

**四个要处理的**：① 基准覆盖不全 → 扩展节点要**明确标记不在基准里**；
② 换基准书 → 映射关系**独立存储、可重建**，别写进节点；③ 粒度拉平（基准粗、
别的书细）→ 先接受；④ 每种语言一个基准。

### 12. 能力分层：第一维度是「用户是否在等」

| | **交互式**（阅读器里，用户在等） | **后台**（批处理，没人等） |
|---|---|---|
| 怎么做 | 预定义 MCP 工具，一次调用返回 | skill 文档 / Codex 自己写脚本 |
| 为什么 | 当场写代码 + 可能失败 = 界面卡住 | 慢无所谓，灵活可演进更值钱 |
| 改动成本 | 高（改四处 + 重编） | 低（改 markdown） |
| 失败语义 | 必须严格，用户会看到 | 可重试、可以问 |

Realtime 时期的 `save_intent_tool` / `run_saved_task` 那套是**对不可靠模型的
妥协**（用确定性换稳定性）。Codex 本身能规划多步、能写脚本，所以那套
**大部分不需要移植**。但有一块必须留下：**数据驱动 + 跨次状态**的部分
（听写的词从哪来、上次做到第几个）—— 形式应是「数据源作为 resource 暴露 +
进度存在我们这边」，而不是「保存的工具」。

### 13. MCP 不慢，慢的是往返次数

实测（生产版本，预热后）：

| | |
|---|---|
| 进程启动 | ~63 ms（一次性） |
| **每次请求边际成本** | **0.17–0.31 ms** |

一次工具调用 ≈ **两次模型往返（1–5 秒 × 2）**，MCP 传输占 0.01%。

**所以成本单位是「调用了多少次」，不是「每次多少毫秒」**：
20 步任务走原子工具 ≈ 40 次模型往返（1–3 分钟）；走一个粗粒度工具 ≈ 2 次。

**推论：工具粒度应按「用户的一句话」切，不是按数据结构切。**
Pi 上原有的 `summarize_section`（取整章而非逐页）、`auto_highlight`
（内部逐页挑句，**只回简报、正文不进上下文**）、`recall_notes`（一次捞
索引+vault+KG+Anki）不是冗余，是**对往返成本的正确回应**。

工具描述的上下文成本：9 个工具 ≈ 2,600 tokens，19 个 ≈ 4,700 tokens。
但 **prompt caching 命中时接近零成本**，所以
**progressive disclosure（分级加载）在交互式场景是净亏** ——
多一次往返（秒级）换省几千个已被缓存的 token，不划算。

### 14. Pi 与 PC 的分工：判据是「瓶颈在 API 配额还是本地算力」

这条判据比「这个任务重不重」有用得多，加新任务时直接可用。

| 任务 | 真实瓶颈 | 放哪 |
|---|---|---|
| KG 建图 | 调 `/usr/bin/claude` CLI（`build_nodes.py` 已 ThreadPoolExecutor 并发） | **Pi** |
| 插图描述 | 调 Claude API（`describe_figures_batch` → `DF._claude_vision`） | **Pi** |
| Google Vision OCR | API | **Pi** |
| YOLO 框图 | 本地推理（`YOLOv10`） | **PC** |
| mokuro OCR | 本地模型（`MangaPageOcr`） | **PC** |
| 页图渲染、字符层 | 本地（`fitz.get_pixmap`） | **iPad 已在做**（`owner: local`） |

调 API 的任务放 PC 上**不会更快** —— 并发上限是额度不是核数，Pi 那颗 ARM 全程
只在等网络。而且它们该留在 24/7 的机器上，夜里 off-peak 慢慢跑。

> 曾错误建议把插图描述、建图一并转 PC。核实后撤回：只有**本地模型推理**
> 值得上 GPU。

**现状（Codex 核实，2026-08-14）**：不是「要不要转移」，**两边 worker 都已存在**。

编排在 `reader_book_ocr.py`，**两个维度正交**：

- `engine = vision | manga` —— Google Vision 还是本地 manga OCR
- `executor = pi | pc` —— Pi `pi-default-v1`（较轻默认链）
  / PC `quality-first-v2`（400 dpi、长边 6000、JPEG95、mokuro polygon geometry、
  DocLayout-YOLO、UniMERNet base）

⚠ **正式执行器不是 `yolo_figures.py`/`mokuro_ocr_book.py`** —— 那两个是
**Pi/旧 standalone 路径**，其 `device="cpu"` / `force_cpu=True` 是有意设置。
Windows 正式执行器是 **`scripts/reader_pc_preprocess_worker.py`**：强制 CUDA、
**不允许 CPU fallback**，manga 用 `MangaPageOcr(force_cpu=False)` 且校验模型确实在
CUDA，DocLayout 同一权重加载到 CUDA，公式走 UniMERNet CUDA。
**4090 在正式 PC 路径会用上；只有直接跑旧 standalone 脚本才仍是 CPU。**

> 曾据 `yolo_figures.py` 判定「4090 完全没被用上」—— 错在看了旧 standalone 路径。
> 查"App/PC 实际跑什么"要认准 canonical 编排入口。

- Manga 换 GPU **只能确认速度提升，不能据此宣称精度提升** —— 两件事别混说
- **调度**：创建 job 时**显式传 `executor=pi|pc`**，非动态调度器。Pi job 立即 spawn；
  PC job 留队列等 Windows 出站 worker 领取，有**分页 checkpoint** 可续跑。
  PC 不在线**不会自动改投 Pi**（长期不开机需用户取消后重建 Pi job）。
  全局 active-job 容量阻止两 executor 同时处理同一本，**避免隐式混跑**
  —— 不自动降级是对的：否则以为拿到 400 dpi、实得较轻链且无从察觉
- **provenance**：canonical 产物（job/page/release/manifest/current）已写
  `engine`/`executor`/`processingProfile`，PC 缓存存完整 quality profile，
  公式写 `latexEngine`；executor/profile 不同的旧未完成 job 会归档后重建，
  **不会在同一 release 里混成半 Pi 半 PC**
- ⚠ **现有 provenance 缺口**：standalone `yolo_figures.py` 的 figure sidecar
  只写 `geom:"yolo"` / `fsrc:"yolo"` / `fconf` / `fcls`，**没有 model file /
  device / profile**。若要独立重跑插图几何，无法分辨哪些页是什么条件下产出的
- ⚠ 已知文档漂移：架构文档写 `quality-first-v1`，代码已是 `v2`（Codex 报告）

**暂不做自动调度**：人工选的隐含好处是你知道每本书用了什么精度；自动调度
要么按"PC 在不在线"选（等于精度随机），要么要一套优先级规则，当前痛点
不值这个复杂度。

### 15. 快照该带什么：判据是「省的往返 vs 占的 token」

实测（第 13 条）：一次工具调用 ≈ 两次模型往返 ≈ 1–5 秒 × 2。
所以凡是「大概率会被用到」的小东西，放快照里是**省一次往返**，划算。

```
状态         activeReading / currentPage / selection / revision …   保留
当前页正文   4000 字符上限                                          ✅ 保留（往返比它贵）
最近动作     recentActions（≤5 条 / 30 秒内 / 限当前书）             ➕ 新增
当前章 KG 节点  name + summary + pages（**用 KG，不另做摘要**）      ➕ 新增（省"找对页"的往返）
大对象       笔迹、页图、整本正文                                    ❌ 按需取
```

**正文 vs 工具 schema 有一处真实区别**：schema 每轮都一样 → prompt cache 命中
→ 成本近零；正文每翻页就变 → cache 必然失效 → 每页重付。但 1200 tokens
比一次往返便宜，所以仍然留在快照里。

**「当前页之外有什么」用 KG，不另做逐页摘要。**

一度打算加逐页摘要（每页一句话）来解决导航。核实后发现**与 KG 节点重叠**，
且 KG 做得更结构化 —— `build_nodes.py` 产出的是三层：

```
{"id":"ladr.l0.ch1","level":0,"parent_id":null,"name":"向量空间","pages":[11,33]}
{"id":"ladr.l1.1A","level":1,"parent_id":"ladr.l0.ch1","name":"R^n和C^n","pages":[12,19]}
{"id":"ladr.l2.…","level":2,"parent_id":"ladr.l1.1A","type":"definition",
 "name":"直和","summary":"和中每元素唯一表示","pages":[12],"numeric_label":"1.41"}
```

每层都有 `pages`，`level:2` 还带 `summary`。AI 拿这个找内容比一句话摘要好用：
有名字、有摘要、有页码、有父子关系。**再做一套摘要是重复投入，还会产生
两份可能互相矛盾的描述。**

所以快照带的是**当前章的 KG 节点**（name + summary + pages），不是新造的摘要。

⚠ **风险仍在**：节点的 `summary` 会给 AI「我已经知道了」的错觉，于是基于它
作答而不取全文 —— 听起来合理但不精确、引用不了原文。**字段要注明这是摘要，
精确引用需取全文**（与截断标注、`unsupported` 不混进空结果是同一类防线）。

**摘要/KG 的适用判据（三条全中才做）**：
**会被反复回访** × **体量大到无法整体加载** × **有稳定标识**

| | 书 | 网页（扩展快照） |
|---|---|---|
| 快照带的是 | 400 页里的第 12 页 | 视口前后，基本就是全部 |
| 存在「别处」吗 | 存在，需要知道去哪找 | 基本不存在 |
| 会回访吗 | 会，反复 | 大多一次性 |
| 稳定标识 | 有（sha） | URL 会变、内容会改 |

**网页三条全不中 → 不做摘要、不建 KG。** 它没有导航问题：你看到的就是全部，
导航是浏览器的事。

**两处 KG 覆盖不到的（已知，暂不处理）**：

1. **KG 是稀疏的** —— 400 页可能只抽 80 个知识点，其余页无锚点。但实际问题
   通常是"讲 X 的那部分在哪"（KG 能答）而非"第 200 页讲什么"（很少见）。
   **这是假设，应在真实使用中验证，而不是现在补一套稠密摘要**
2. **不是所有书都适合 KG** —— 教材有知识结构；非虚构叙事（《盐糖脂》
   《创世纪的第八天》）抽"知识点+前置"意义不大，它们要的导航是脉络与人物。
   **等真碰到痛点再看它需要什么形式，现在设计多半设计错**

### 16. piggyback：加进快照即可，不需要独立机制

**论证修正**：曾说它的价值是「低延迟」—— 错。推送模式下 App→Pi→PC 只有
几十毫秒，而用户从操作到开口通常一两秒，同步早完成了。

**它的真正价值是可靠性**：对话走 WSS 到桥接，同步走另一条链路，**一条通不代表
另一条通**。同步服务挂了、Pi 忙、PC 刚开机在追赶时，语音照常工作而数据是陈旧的，
且 AI 不知道。piggyback 让「用户刚做的事」不依赖同步链路的健康。

这个区别决定了它该带什么：**带「动作」不带「数据」**。

| 带 | 不带 |
|---|---|
| 最近 N 秒的动作（划线 / 翻页 / 点词 / 写便签） | 别的书的变更 |
| 当前书、当前页范围内的 | 历史累积状态 |
| 刚划的那句原文（极小且极可能被问到） | 完整高亮列表（那是数据，调工具取） |

**数据源已有**：`reader-outgoing-context` 的 `page.context` / `focus` / `drawing` /
`command` 事件就是"用户刚做了什么"。快照加一个 `recentActions` 字段装最近 N 条即可，
推送模式下 AI 每轮读最新快照就够 —— **不需要在对话时另做一次 piggyback**。

四条约束：≤5 条、30 秒窗口、限当前书、**字段名本身表明是"刚发生的动作"而非
待办指令**（不标注的话 AI 可能读成"用户要我处理这句"，那就成了干扰）。

### 17. 同步的传输与时机

- **Pi → Windows 改推送**（复用已有 WSS），延迟从拉取模式的 0–15 分钟降到几十毫秒。
  延迟的来源从来不是"经过了 Pi"，是"拉还是推"
- **同步服务给显式高优先级**（`Nice=-5` 之类）。现在 `yolo-figures.service` 用
  `Nice=19/CPUWeight=20` 压低，同步应反向显式提高 —— 不设的话，某夜批处理
  跑起来同步莫名变慢，且很难联想到原因
- **不做 iPad↔Windows 直连**：两条路径的去重与排序不值那点延迟收益。
  保持 Pi 为**唯一顺序权威**
- **启动器**（Codex 已做，开关所有服务）承担两件事：**追赶同步** + **领取待办计算任务**
  - 拉增量不拉全量，需要"上次同步到哪"的水位
  - 离线太久 → 拉快照 + 追增量
  - 失败必须出声：启动阶段静默失败最要命，用户以为一切就绪
- ⚠ **同步未完成时，AI 不得下否定性结论**。PC 刚开机、同步还在跑时问
  "我昨天划的那句在哪"，查本地副本没找到就答"你没划过" —— 数据没错、代码没错、
  **时机错了**。把"同步中 / 已就绪"作为新鲜度的一部分暴露，AI 看到"同步中"
  只能说"还在同步，暂时查不到"

### 18. 载体与依赖方向：PWA 废除，扩展只依赖 App

**PWA 立即废除**（2026-08-14 拍板）。理由不是它做得不好，是覆盖面：
**几乎所有桌面浏览器都支持扩展，但对 PWA 的支持参差**。完整阅读能力由
iOS App 与浏览器扩展提供，Pi 不再提供一份 App 已经能提供的阅读界面。

已实现：`_server_deploy/reader_pwa_retirement.py` 拦五个页面入口
（`/pdf/`、`/pdf/search`、`/pdf/epub/view`、`/pdf/fav/view`、`/pdf/html/view`），
返回 **410 + 说明页**。

- 用 410 不用 404：404 会被当成"坏了"，有人去查为什么路由丢了；
  410 的语义是"这里以前有，现在有意撤掉"。响应带 `X-BW-Reader-Retirement`，
  日志里能把"有意下线"与"真的坏了"分开
- 按 endpoint 拦不按 path：endpoint 覆盖同一处理器的所有 URL 变体，按 path 会漏
- **只关页面，`/pdf/api/*` 一律不动** —— App 与扩展还要用那些服务端能力

### 19. iPad 上扩展只管网页，书籍完全归 App

**产品边界（2026-08-15 拍板）**：iPad 上**扩展在书籍阅读器场景里没有角色**。
真书由 App 全权负责，扩展只管普通网页。其它浏览器（Windows Chrome 等）
没有 App 依附，等以后单独做新扩展。

**这条推翻了同日早些时候的一次尝试**，记录始末以免重来：

曾判断「扩展把高亮写去 Pi、App 的在 IndexedDB，两份数据割裂」，据此做了
路由分流（10 条 App-owned 路由改指向 App 本机服务）+ 落点机制
（App 经 App Group 把端口与 capability token 交给扩展）。**已全部撤回**。

撤回原因是那个割裂在 iPad 的网页场景下**并不存在**：

- 扩展在普通网页上的高亮早已完全本地化 —— `src/web-highlights.js`，
  存 `webHighlightsV1`，exact quote + prefix/suffix + DOM 位置复合锚，
  CSS Highlights API 渲染，不碰任何 `/pdf/api/*`
- 那 10 条的调用点在 `src/pwa-adapter.js`（403 行）与 `src/shell.js`（623 行），
  两者第一行就是门：`if (!RC || !RC.use || !bridge) return;`
  需要 `window.__bwPwaBridge` / `__bwRoot`，**普通网页两者都没有**。
  这 1000 余行在 iPad 网页场景下一行都不执行

**错因（同日第二次犯同一个错）**：把「源码里出现这条路径」当成「它会被执行」。
第一次是把 `BW_FETCH_ROUTE_METHODS`（允许清单）当成调用记录；
第二次是没检查模块的激活条件。**判断依赖必须看两样：真实调用点，
以及那段代码在目标场景下会不会运行。**

**遗留待办**：`pwa-adapter.js` / `shell.js` 里的书籍分支是死代码，应整块退役。
它们不执行所以无害，但留着会让下一个人重复上面的误判。

### 20. ~~落点机制与硬失败~~（已撤回）

App 经 App Group 向扩展公布本机服务落点、扩展硬失败不回落 Pi ——
这套设计**随第 19 条一起撤回**，因为它服务的场景不存在。

其中两条判断本身仍然成立，将来若真需要扩展访问 App 数据可以复用：

- **硬失败优于回落**：回落看起来友好，实际是把割裂藏起来 —— 用户以为存上了，
  换个入口就不见了。宁可当场说「请先打开 App」
- **拿不到落点的三种原因必须分开**（App 没开 / App Group 配置坏 / 旧版 App
  无此字段），因为三者分别指向：用户自己开 App、看日志、更新 App

### 21. Pi 的 CLI 包装成 API，消除「Pi 网关」这个概念

现在代码里有 `nativePiFetch`、`owner: "pi"`、`BW_PI_GATEWAY_UNAVAILABLE` ——
**Pi 被当成一种特殊的东西对待**，有专门的分支、错误码、转发机制。

把 Pi 上的 CLI 调用包装成 HTTP API 之后，它跟 Anthropic、Google 的 API 就是
同一类：一个需要网络的服务端点。心智模型从三类（local / native / pi）
**降成两类（本机 / 联网）**，换端点、加备用、离线降级都是同一套逻辑。

Pi 真正不可替代的只剩一个角色：**同步中继**（永远在线、事件顺序权威、备份）。

## 二之二、踩过的坑（省下次的核实）

- **同一份前端有两个副本**：`_server_deploy/static/pdf/`（源）与
  `ios/BWReader/Generated/ReaderBundle/static/pdf/`（App 实际加载）。
  行数都不同。查"App 里实际跑什么"必须看后者。
  曾据源码目录判定"离线词典没接上"，实际打包版里 `rc-wordpop.js` 早已接上
  （日语走本地、英语仍走 Pi）
- **`ios/BWReader/Extension/Resources/` 是构建期由 `package_safari.py` 生成的**，
  改扩展要改 `extensions/bw-reader-webext/` 源
- **`project.yml` 的 `Shared/` 是逐文件列举**，新文件不会自动进 target，
  漏了就是编译失败。三个 target：BWReader / BWReaderSafariExtension / BWReaderWidget
- **`background.js` 被大量测试以 vm 沙箱逐段提取**，不能在其中引入模块级依赖。
  曾因此打破 7 个既有测试（`BWRouteDestination is not defined`）。
  解法是解耦而非改测试：缺模块时安全落 `"pi"`，调用点比较字面量 `"app"`
  并用一条断言把字面量与常量钉在一起 —— 否则分支永远不成立、请求静默继续打 Pi
- **「源码里出现」≠「在用」**：`BW_FETCH_ROUTE_METHODS` 是允许清单，不是调用
  记录。据它列出的 14 条「扩展依赖」里，10 条从未被调用过。判断依赖要看
  真实调用点及其触发条件（`hostMode === 'html'` 这种条件本身就说明它属于 PWA）
- **单文件二进制的 `grep` 不可信**：曾 grep 189MB 单文件发布的桥接，
  漏报三个工具、又把无关字符串当成工具名。要问它自己（`--self-test` / `tools/list`）
- **`tests/reader_contract/` 已 125 个文件**，一次跑完接近 10 分钟命令上限，
  需分两批
- **Direct 的消息上限是 256 KiB，不是 64 KiB**（`DirectBridgeContract
  .MaximumMessageBytes` 与 `rc-computer-voice.js` 的 `MAX_MESSAGE_BYTES`
  都是 262144）。曾按 64 KiB 写过 `ReaderQuery.MaximumResultBytes` 的理由。
  数值（40 KiB）不必改，但**真正的约束是上下文预算不是帧限** ——
  40 KiB 已约 12k token。⚠ 别据「上限是 256 KiB」去放宽：
  TF309 的 Swift 侧一度仍是 64 KiB 且严格相等校验，两端版本会错开
- **副本目录不要跟权威目录同名**：KG 副本落在 `state/kg-mirror/` 而非
  `knowledge_graph/`。同名时哪天电脑侧也跑建图，只读副本会覆盖掉带掌握度的
  权威文件 —— 而掌握度是唯一不能重算出来的那部分。路径本身就该说清它是什么
- [ ] **安全排查**：照 OpenClaw 的攻击面查一遍
      （silent binding fallback、ClawJacked 式本地 WebSocket 爆破）

## 三、外部参考

- **Hermes Agent**（Nous Research, 2026-02）：skill = `~/.hermes/skills/<n>/SKILL.md`，
  markdown + YAML frontmatter（`name`/`description`/`triggers[]`），**不是可执行代码**，
  是给 LLM 看的步骤说明 + 已知陷阱 + **验证步骤**。progressive disclosure 分级加载；
  SessionDB 用 FTS5 全文索引，检索 = 搜索 + LLM 总结。
  承认 skill 库会退化（"没有整理会攒 500 个平庸 skill"），靠定期 review，**无自动衰减**
- **OpenClaw**（原 Clawdbot，60 天 25 万 star）：local-first 自托管，
  Gateway 单端口（默认 18789）多路复用 WebSocket + HTTP + 渠道消息；
  heartbeat 定时唤醒巡检本地文件与远程库。
  ⚠ **skill 目前是 full trust in-process**，权限清单 `skill.yaml`
  （network/filesystem/shell/credentials）仍是提案（issue #12219 / #28298），
  网上说的"编译成 WASM 沙箱"**不实**。
  安全审计 `openclaw security audit` 覆盖 12 类 50+ 检查，可作对照清单
- 与 **LSP** 的差距：增量同步（我们每次推全量正文）、能力协商（我们运行时
  返回 unsupported 试错）、`$/cancelRequest`（我们没有）、部分结果流式。
  文档版本号 + 回执比对我们**有**（`snapshotRevision`）
